# БЕТА 1 · підключення власної бази Firebase

Повна покрокова інструкція також доступна **в самому додатку**: «Інструкція» на стартовому екрані, «Простір → Інструкція» або кнопка «?» у «Командах». Виберіть розділ «Власна база», «Учасник» чи «GitHub». Цей файл — її текстова довідка. Майстер підключення: **«Команди → Бази → Підключити базу»**. Код застосунку й Firestore Rules входять у проєкт. **Хмарний проєкт, мережеві акаунти й базу створює адміністратор; вони не створені заздалегідь.** Початкове налаштування й перший акаунт можна створити в браузері. Для адміністративного скидання паролів передбачений окремий інструмент для Node.js 24 у довіреному середовищі; постійний сервер не потрібен.

Поки використовуйте вигадані тестові дані. Перевірки в Emulator Suite не замінюють тестування вашого проєкту, двох фізичних телефонів та незалежну перевірку безпеки.

## 1. Створіть проєкт

1. Відкрийте [Firebase Console](https://console.firebase.google.com/) під Google-акаунтом адміністратора та створіть окремий проєкт.
2. Залиште тариф **Spark**. Для цього сценарію Google Analytics не потрібна; її можна не вмикати. Не підключайте billing / Blaze лише заради майстра.
3. У **Project settings → General → Your apps** додайте Web app кнопкою `</>`. Firebase Hosting не потрібен: сайт працює на GitHub Pages.
4. Збережіть показані налаштування `firebaseConfig`.

Це власний проєкт адміністратора всередині інфраструктури Google. Користувачі інших незалежних підрозділів можуть підключати інші проєкти до того самого сайту з вашого репозиторію. Їм не потрібно копіювати репозиторій чи змінювати його код. Налаштування, акаунт, ключі й історія кожної бази зберігаються окремо всередині локального простору. Конфігурації користувачів не записуються до GitHub і не надсилаються в спільну базу видавця. Водночас усі довіряють коду та оновленням видавця цього сайту. Учасники однієї команди користуються **одним і тим самим** Firebase-проєктом. [Налаштування Firebase Web app](https://firebase.google.com/docs/web/setup)

## 2. Увімкніть вхід і створіть Firestore

1. **Build → Authentication → Get started → Sign-in method → Email/Password**: увімкніть звичайний Email/Password. Він використовується з технічною адресою, сформованою з логіна; особиста поштова скринька користувачам не потрібна. Email link, Google sign-in та телефонний вхід для цього майстра не потрібні.
2. У **Authentication → Settings → Authorized domains** додайте домен вашого сайту, наприклад `OWNER.github.io`, **без** `https://` і `/REPOSITORY/`. Якщо тестуєте локально й отримали помилку домену, додайте відповідний localhost-домен.
3. **Build → Firestore Database → Create database**: створіть стандартну базу `(default)`, виберіть регіон свідомо та почніть із **production mode**. Відкритий test mode не потрібен.
4. У вкладці **Rules** замініть початкові правила повним вмістом [firebase/firestore.rules](../firebase/firestore.rules) із цього випуску та натисніть **Publish**. Цей самий файл можна завантажити в майстрі застосунку.
5. У **Indexes → Composite → Add index** створіть індекс: **Collection ID `events`**, поле **`pending` — Array contains**, поле **`createdAt` — Ascending**, **Query scope — Collection**. Дочекайтеся готовності індексу. Його точний опис — [firebase/firestore.indexes.json](../firebase/firestore.indexes.json), також доступний для завантаження в майстрі.

Правила — частина контролю доступу, а не необов’язковий приклад. Не замінюйте їх на `allow read, write: if true`. Публікація сайту на GitHub Pages сама собою не публікує Firestore Rules або індекси. [Email/Password](https://firebase.google.com/docs/auth/web/password-auth), [початкові Firestore Rules](https://firebase.google.com/docs/firestore/security/get-started), [керування індексами](https://firebase.google.com/docs/firestore/query-data/indexing)

## 3. Видайте перший логін через Console

Логін має містити **3–32 латинські символи**: малі літери `a–z`, цифри, `_` або `-`; перший і останній символ — літера або цифра. Великі літери застосунок перетворює на малі. Для прикладу логін — `admin_1`, ID проєкту — `my-project-123`.

1. У **Authentication → Users → Add user** створіть акаунт із технічною адресою **`admin_1@my-project-123.invalid`**. Замініть обидві частини своїми значеннями: точна формула — `логін@projectId.invalid`.
2. Задайте випадковий тимчасовий пароль щонайменше з 20 символів, наприклад з генератора менеджера паролів. Скопіюйте **UID** створеного користувача.
3. У **Firestore Database → Data** створіть колекцію **`USERS`** (великі літери) та документ **`admin_1`** (сам логін, без email).
4. Додайте лише ці поля:

| Поле | Тип у Console | Значення |
| --- | --- | --- |
| `uid` | string | UID цього Auth-користувача |
| `enabled` | boolean | `true` |
| `mustChangePassword` | boolean | `true` |
| `resetAfter` | number | `0` |

Пароль і його хеш до цього документа **не додаються**. Обліковими даними керує Firebase Authentication. Звичайний вебклієнт не може створити `USERS` або призначити собі UID/дозвіл. У застосунку немає самостійної реєстрації. Навіть якщо сторонній клієнт створить Auth-акаунт, без належного адміністративного запису `USERS` він не отримає командні дані.

Для інших учасників повторіть ці дії з окремими логінами або скористайтеся інструментом у розділі 7. Не діліться одним акаунтом між людьми й не перейменовуйте його технічну адресу вручну: вона є частиною зв’язку логіна з UID.

## 4. Підключіть простір і встановіть власний пароль

1. Відкрийте ваш HTTPS-сайт, створіть або розблокуйте локальний простір.
2. **«Команди → Бази → Підключити базу»**: вставте налаштування Web app у **«Налаштування Firebase»** та натисніть **«Зберегти базу»**.
3. Введіть видані **«Логін»** і тимчасовий **«Пароль»**, натисніть **«Увійти»**. У полі логіна не вводьте технічну email-адресу.
4. У формі **«Встановіть власний пароль»** введіть новий пароль двічі: **12–128 символів**, можна довгу фразу, без керівних символів. Він має відрізнятися від тимчасового. Натисніть **«Зберегти пароль»**.
5. Скопіюйте показаний **Firebase UID**. Це той самий UID із Console; його можна використати для початкового власника бази.

PIN локального простору й мережевий пароль виконують різні функції. Пароль вводиться для входу; він не є ключем шифрування задач. Вихід із простору або команд завершує мережевий сеанс; вхід знову може вимагати пароль. Свій пароль можна змінити кнопкою **«Змінити пароль»**. Якщо забули його — зверніться до адміністратора. Поштового відновлення немає, а скидання мережевого пароля не відновить забутий PIN або втрачені ключі простору.

Якщо Auth уже змінив пароль, а збереження позначки `mustChangePassword` завершилося помилкою, застосунок про це повідомить. Новий пароль уже діє: повторіть завершення операції; після перезавантаження входьте **новим** паролем. Позначка обов’язкової зміни керує штатним інтерфейсом, але Rules не можуть перевірити факт зміни пароля в Auth: це не криптографічний доказ проти зміненого клієнта.

Приклад публічного config; усі значення замініть власними з Console:

```json
{
  "apiKey": "YOUR_WEB_API_KEY",
  "authDomain": "YOUR_PROJECT.firebaseapp.com",
  "projectId": "YOUR_PROJECT",
  "appId": "YOUR_WEB_APP_ID"
}
```

Web config та його API key — публічні параметри клієнтського проєкту, а не пароль доступу до Firestore. Доступ перевіряють Firebase Authentication і Security Rules. **Не вставляйте service account JSON, `private_key`, Admin SDK credentials або секрети серверів.** Додавати config до коду чи GitHub Secrets також не потрібно. [Firebase API keys](https://firebase.google.com/docs/projects/api-keys)

## 5. Закріпіть початкового власника через Console

У **Firestore Database → Data** створіть рівно такий документ:

| Поле | Значення |
| --- | --- |
| Collection ID | `system` |
| Document ID | `bootstrap` |
| Field | `ownerUid` |
| Type | `string` |
| Value | UID вашого мережевого акаунта, скопійований у попередньому кроці |

Шлях документа: **`/system/bootstrap`**. Збережіть його та поверніться до застосунку. Оновіть підключення або повторно відкрийте базу й створіть команду.

Цей документ змінюють тільки через Firebase Console або інші привілейовані адміністративні інструменти власника проєкту. Клієнтські Rules забороняють його створення, зміну й видалення з вебдодатка. Право створювати команди отримує саме вказаний UID; принципу «хто зайшов першим — той власник» немає. Погоджувати інших учасників уже створеної команди можна через її інтерфейс.

## 6. Запросіть учасника

1. Створіть команду, відкрийте її та натисніть **«Запросити»**.
2. Створіть кандидату окремий акаунт і передайте його **логін, тимчасовий пароль**, публічний config **цього самого проєкту** та одноразовий код узгодженим захищеним каналом. Код діє менше 15 хвилин і дає право подати запит, а не автоматичний доступ до текстів.
3. Кандидат відкриває власний локальний простір, підключає базу, входить за виданим логіном, встановлює власний пароль і вводить запрошення.
4. Адміністратор звіряє людину й відбиток її ключа окремим узгодженим каналом та погоджує заявку. Після отримання ключа й зашифрованого знімка учасник бачить командні задачі.

Не передавайте пароль адміністратора учасникам. Назва простору, логін і сам код запрошення не доводять особу людини. Один Firebase UID прив’язується до однієї криптографічної ідентичності простору; інший простір із новими ключами не повинен непомітно замінювати її.

## 7. Адміністративний інструмент: створення та скидання

Інструмент **`scripts/manage-accounts.mjs`** є у вихідному репозиторії та `NaKontroli-GitHub.zip`, але не в опублікованих файлах Pages. Запускайте його з кореня розпакованих вихідних файлів тільки на довіреному комп’ютері адміністратора або у власному Cloud Shell. Звичайним учасникам Node.js та адміністративні права не потрібні.

Потрібні Node.js 24, залежності `npm ci` та **Application Default Credentials (ADC)** із правами керування Auth і Firestore у вибраному проєкті. Інструмент задає project ID явно через `--project`. Він не приймає пароль або JSON credentials аргументами.

Для локальних користувацьких ADC Firebase Auth вимагає власний OAuth client типу **Desktop app**: стандартні облікові дані самого `gcloud` можуть бути відхилені. Створіть Desktop OAuth client у Google Cloud Console цього проєкту, збережіть його JSON **поза папкою сайту й репозиторієм** та виконайте наведений в офіційній інструкції вхід. Налаштування consent screen та права Google-акаунта залежать від вашої організації. У Cloud Shell так само потрібні сумісні ADC; відкритий Google-сеанс у браузері сам по собі не є credentials інструмента. [Firebase Admin: ADC і gcloud](https://firebase.google.com/docs/admin/setup#testing_with_gcloud_end_user_credentials)

```sh
gcloud auth application-default login --client-id-file=/private/path/oauth-desktop-client.json
npm ci
```

Не завантажуйте ADC, service account JSON, приватні ключі або паролі в GitHub, Web config чи `dist`. Admin SDK працює з підвищеними правами поза клієнтськими Rules; зберігати його credentials у вебдодатку не можна.

Перевірка назви без мережі, credentials або створення пароля:

```sh
node scripts/manage-accounts.mjs create --project my-project-123 --login officer_1 --dry-run
```

Створення та скидання, коли ADC налаштовані:

```sh
node scripts/manage-accounts.mjs create --project my-project-123 --login officer_1
node scripts/manage-accounts.mjs reset --project my-project-123 --login officer_1
```

Замініть `my-project-123` і логін своїми. Після успіху інструмент покаже UID і **новий випадковий 32-символьний тимчасовий пароль**. Передайте його лише відповідній людині. Не запускайте команду в публічному CI та не публікуйте її вивід. Пароль не передається в shell-аргументах і не записується у Firestore. Наявний логін або Auth-акаунт `create` не перезаписує.

Під час `reset` інструмент перевіряє відповідність UID і технічної адреси, атомарно вимикає дозвіл `USERS`, змінює пароль Auth, відкликає refresh tokens і лише потім повертає дозвіл із `mustChangePassword: true` та новим `resetAfter`. **UID та прив’язка ключів зберігаються.** Rules вимагають `auth_time > resetAfter`: новий вхід має відбутися щонайменше з наступної секунди. Інструмент показує `signInAfter`; якщо вхід зроблено надто швидко, зачекайте й увійдіть знову. Годинник адміністративного пристрою має бути правильним. Старий пароль більше не підходить, а токени зі старим часом входу не отримають командні дані. [Керування Auth-користувачами](https://firebase.google.com/docs/auth/admin/manage-users), [відкликання сеансів](https://firebase.google.com/docs/auth/admin/manage-sessions)

**Auth і Firestore не становлять одну транзакцію.** Якщо операція перервалася після вимкнення доступу, він залишається вимкненим. Звичайний `reset` відмовиться працювати з таким записом: це захищає від паралельного скидання та випадкового ввімкнення навмисно заблокованої людини. Перевірте Auth і `USERS` у Console, усуньте причину та переконайтеся, що інший адміністратор уже не виконує операцію. Лише тоді один адміністратор може явно продовжити:

```sh
node scripts/manage-accounts.mjs reset --project my-project-123 --login officer_1 --resume
```

`--resume` генерує ще один новий пароль. Не запускайте його паралельно. Фінальне ввімкнення перевіряє версію документа й не перезаписує проміжні зміни іншого адміністратора. Після мережевої помилки останнього запису його результат може бути невідомий — інструмент позначить `stateUncertain`; перевірте Console перед повтором. Інструмент ніколи не видаляє Auth-акаунт для «очищення» невдалої операції.

Якщо `create` устиг створити Auth, але не документ `USERS`, перевірте технічну адресу й UID у Console. Відновіть `USERS/{логін}` із **тим самим UID**, `enabled: false`, `mustChangePassword: true`, `resetAfter: 0`, після чого виконайте перевірене `reset --resume`. Не прив’язуйте логін до нового UID і не перепризначайте чужий запис.

Якщо у попередньому випуску 2.0 уже був тестовий акаунт зі звичайною email-адресою, автоматичного перенесення немає. Адміністратор має зберегти його Auth UID, командну прив’язку й локальний простір, через довірений Admin SDK `updateUser` змінити лише email на вільну технічну адресу `логін@projectId.invalid` та створити відповідний `USERS/{логін}`. Для видачі нового тимчасового пароля після цього використовується звичайне скидання. **Не видаляйте й не створюйте Auth-користувача заново.** Команди `create` і `reset` не виконують таку міграцію; `reset` навмисно відмовляє, доки UID і технічна адреса не збігаються.

Видалення поля чи «хеша» у Firestore **не скидає пароль Auth**. Для забутого пароля використовуйте `reset`, а не видалення акаунта. Зміна пароля або вимкнення дозволу також не стирає дані, які пристрій уже отримав локально, і не замінює відкликання ключів.

## Що зберігається й очищається

Особисті задачі залишаються в локальному просторі. Для команд Firestore зберігає зашифровані конверти та метадані доступу: логін і дозвіл `USERS`, UID, відкриті ключі, членство, ролі, призначення, версії, поточні позначки виконання й підтвердження доставки. Текст задач, назва команди, історія та час виконання містяться в зашифрованому вмісті. Auth окремо обробляє технічні email-акаунти та паролі; у Firestore паролів і їхніх хешів немає.

Адресат перевіряє конверт, зберігає подію, маркер повтору й майбутній ACK у зашифрованому IndexedDB, потім підтверджує отримання. Після всіх необхідних ACK авторизований клієнт може прибрати транспортний шифротекст. Локальна історія та мінімальні серверні записи доставки/версій залишаються. **Строку автоматичного видалення конверта немає.** Якщо одержувач лишився офлайн або втратив пристрій до ACK, шифротекст може зберігатися невизначено довго. Така доставка лишається непідтвердженою; примусове очищення не реалізоване.

**Cloud Functions і Firestore TTL не використовуються.** Очищення виконується під час роботи підключеного клієнта, з перевірками Rules; коли всі застосунки закриті, фізичне очищення відкладається. Видалення документа не гарантує негайного стирання всіх копій провайдера або одержувачів.

## Spark і типові проблеми

Безкоштовна квота Firestore: одна база на проєкт, 1 GiB даних, 50 000 читань, 20 000 записів і 20 000 видалень на добу, 10 GiB вихідного трафіку на місяць. Перепідключення, синхронізація й перевірки правил витрачають ресурси. Cloud Functions потребують Blaze, а TTL deletes — увімкненого billing; майстер не вмикає їх. Квоти можуть змінюватися. [Firestore billing](https://firebase.google.com/docs/firestore/pricing), [Cloud Functions](https://firebase.google.com/docs/functions/get-started)

| Повідомлення / ситуація | Що перевірити |
| --- | --- |
| Email/Password вимкнено | Увімкніть провайдер у Authentication цього проєкту. |
| Логін або пароль не підходить | Логін — без `@`; адміністратор має створити технічний Auth-акаунт і точний запис `USERS/{логін}`. Після скидання потрібен новий тимчасовий пароль. |
| Доступ вимкнено / сеанс застарів | Перевірте `enabled`, UID і `resetAfter`; після скидання зачекайте наступної секунди й увійдіть заново. Вимкнений доступ відновлює лише адміністратор. |
| Некоректний config / API key | Повторно скопіюйте Web app config; це не service account JSON. |
| `failed-precondition` / потрібен індекс | Створіть складений індекс `events: pending Array contains, createdAt Ascending`, scope Collection, і дочекайтеся готовності. |
| `permission-denied` | Опублікуйте повний файл Rules; перевірте `(default)`, документ `USERS` і точний `ownerUid`. |
| UID є, команду створити не можна | Створіть `/system/bootstrap` через Console із цим UID; перевірте, що відкрили потрібну базу. |
| Запрошення не працює | Учасник має підключити той самий `projectId`; код одноразовий і діє менше 15 хвилин. |
| Квоту вичерпано / мережа недоступна | Збережена локальна черга чекає повторної синхронізації; це не підтвердження доставки. |
| Старий localhost-прототип | Він лишається локальним архівом і не переноситься в Firebase автоматично. |

У тестовій команді — до 30 учасників і до 12 етапів на задачу. Видалення учасника, пониження адміністратора, ротація ключів і окрема реєстрація другого пристрою ще не реалізовані. Копію JSON не запускають одночасно на двох пристроях: вона клонує ключі й командну ідентичність.

Rules не перевіряють криптографічні підписи: некоректну подію клієнт ізолює без ACK, продовжуючи обробляти інші незалежні коректні події. Якщо вона вже змінила серверну версію задачі, для відновлення потрібна надійна локальна копія адміністратора. Двадцять п’ять некоректних непідтверджених подій можуть заповнити поточну вибірку й затримати пізніші. Некоректний відбиток кандидата блокує його погодження. Захист від такого зловживання допущеним учасником ще потребує розвитку; гарантії захисту від спаму й блокування черги в прототипі немає.

Перед використанням будь-яких реальних службових даних потрібні повна модель відкликання, відновлення й керування пристроями, перевірка розміщення, незалежний аудит та рішення відповідальних за безпеку. Чотиризначний PIN і тестова інтеграція не дають такої гарантії.
